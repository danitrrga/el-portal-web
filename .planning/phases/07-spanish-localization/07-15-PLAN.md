<objective>
Emit the SEO signals that make both language versions findable: per-locale
titles and descriptions on all 16 pages, `hreflang` alternates including
`x-default`, per-locale Open Graph and Twitter tags, and a sitemap covering both
locales.

Purpose: this is the requirement the whole detection decision was made to
protect. `07-RESEARCH.md` §1 rejected blanket redirection because Googlebot
crawls from the US and sends no `Accept-Language`, which can leave one locale
permanently unindexed. Explicit signals — distinct URLs, `hreflang`
annotations, and a sitemap listing both — are what replaces that implicit
detection. Without them, `/es/*` exists and is invisible.

Six of the eight routes currently export no metadata at all and inherit a single
site-wide title. That was tolerable for one locale; with two it means a Spanish
page rendering Spanish content under an English title, which is exactly what
success criterion 5 forbids.

This plan is sequenced after every copy plan so descriptions are written against
the page copy that actually shipped, not against a draft.

Every artifact this plan emits — canonicals, alternates, OG urls, the sitemap —
is an absolute URL built from one environment variable. If that variable is
wrong, all four are wrong sitewide and Google is the one that notices. Task 1
therefore starts by confirming it rather than trusting the value written into
this plan.

Output: catalogue-driven metadata for all 16 pages, a both-locale sitemap, and
no route dropped from the static build.
</objective>

is invisible in every local check this phase runs.

Write `src/messages/es/metadata.json` as the key-identical Spanish mirror.
Descriptions are marketing copy and are bound by `SPANISH-VOICE.md` exactly like
any other string: no written subject pronoun, no `usted`, no exclamation marks,
none of the 16 anti-words, product nouns resolved through `GLOSSARY.md`. Search
snippets are where a register slip is most publicly visible.

Keep titles inside the length search engines display and descriptions inside
theirs. Spanish runs 15-25% longer, so a description translated literally from a
tight English one will truncate in results. Write the Spanish description to fit
rather than translating and hoping.

Implement `buildPageMetadata(locale, route)` in `src/lib/seo.ts`:

  - set `title` and `description` from the catalogue;
  - set `alternates.canonical` to this locale's own URL for the route;
  - set `alternates.languages` with an entry for `en`, an entry for `es`, and an

    including on `/` itself, where the set is `en: /`, `es: /es`,
    `x-default: /`. `x-default` is what tells a crawler which version to show a
    user whose language matches neither, and getting it wrong on `/` is what
    would make `/es` the canonical home page;
  - set `openGraph` with `locale` (`en_US` and `es_ES`), `alternateLocale`, the
    canonical `url`, `title`, `description` and `siteName`;
  - set `twitter` card metadata mirroring the OG values.

Build every URL from the confirmed `NEXT_PUBLIC_SITE_URL` plus
`ROUTE_PATHS[route]`, with the `/es` prefix applied only for the Spanish locale —
that single helper is what keeps `as-needed` prefixing correct in the canonical,
the alternates, the OG url and the sitemap simultaneously. Write it once and use
it everywhere; four hand-built URL strings will disagree within a month.

In `src/app/[locale]/layout.tsx`, add `metadataBase` from the same confirmed
