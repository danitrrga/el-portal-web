<objective>
Emit the SEO signals that make both language versions findable: per-locale
titles and descriptions on all 16 pages, `hreflang` alternates including
`x-default`, per-locale Open Graph and Twitter tags, and a sitemap covering both
locales.

Purpose: this is the requirement the whole detection decision was made to
protect. `07-RESEARCH.md` §1 rejected blanket redirection because Googlebot
crawls from the US and sends no `Accept-Language`, which can leave one locale
permanently unindexed. Explicit signals — distinct URLs, `hreflang`
annotations, and a sitemap listing both — are what replaces that implicit
detection. Without them, `/es/*` exists and is invisible.

Six of the eight routes currently export no metadata at all and inherit a single
site-wide title. That was tolerable for one locale; with two it means a Spanish
page rendering Spanish content under an English title, which is exactly what
success criterion 5 forbids.

This plan is sequenced after every copy plan so descriptions are written against
the page copy that actually shipped, not against a draft.

Output: catalogue-driven metadata for all 16 pages, a both-locale sitemap, and
no route dropped from the static build.
</objective>

Implement `buildPageMetadata(locale, route)` in `src/lib/seo.ts`:
  - read the route's values with `getTranslations({ locale, namespace: 'metadata' })`,
    passing the locale explicitly rather than relying on request scope, since
    this runs inside `generateMetadata`;
  - set `title` and `description` from the catalogue;
  - set `alternates.canonical` to this locale's own URL for the route;
  - set `alternates.languages` with an entry for `en`, an entry for `es`, and an
    `x-default` entry pointing at the English URL. `x-default` is what tells a
    crawler which version to show a user whose language matches neither — and it
    must point at `/`-relative English, the URL the proxy negotiates from;
  - set `openGraph` with `locale` (`en_US` and `es_ES`), `alternateLocale`, the

and the sitemap simultaneously. Write it once and use it everywhere; four
hand-built URL strings will disagree within a month.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| site config -> emitted absolute URLs | metadata and sitemap publish canonical URLs crawlers follow |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-15-01 | Spoofing | canonical and alternate URLs | mitigate | All URLs are built from `NEXT_PUBLIC_SITE_URL` plus the static `ROUTE_PATHS` table through one helper; no request-derived host or path reaches a canonical, so a Host-header injection cannot rewrite the site's own canonical URLs |
| T-07-15-02 | Tampering | pointing canonicals at the application origin | mitigate | The plan names both env vars explicitly and requires the site URL, not `NEXT_PUBLIC_APP_URL`; a canonical pointing at the app would de-index the marketing site |
| T-07-15-03 | Information disclosure | metadata catalogue content | accept | Titles and descriptions are public marketing copy by definition; no internal path, staging host or configuration value is emitted |
| T-07-15-04 | Denial of Service | metadata generation forcing dynamic rendering | mitigate | Prerender-manifest assertion re-run after the change; a route silently becoming dynamic would show up as a missing entry rather than as a passing build |
| T-07-15-SC | Tampering | package installs | accept | This plan installs nothing |
</threat_model>
