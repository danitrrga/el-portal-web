# Phase 07 — UI Design Contract: Spanish Localization

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope framing — read first

This phase is **content + routing, not a visual redesign**. The desktop design is
frozen (Phase 5, RESP-08 + override OVR-01) and Phase 5's mobile type scale was
tuned to exact measured `clamp()` values and verified line counts at
320/360/390/430px. **Nothing in this document authorizes changing those tuned
values as a blanket fix.** The only genuinely new UI surface is the language
switcher (locked in `07-CONTEXT.md` D-10/D-11/D-12). Everything else in this
contract exists to specify the **second-order visual consequences of translation**
that nobody has specified yet: text expansion, containment-harness behavior,
uppercase accented glyphs, punctuation, and the small set of layout-sensitive
components where a longer string can break a fixed-width or no-wrap assumption.

## Typography

**Inherited unchanged** — the type scale, `.display` utility, and every
`clamp()` value Phase 5 tuned are LOCKED for this phase. This phase adds a
**Spanish rendering contract** on top, because it is the surface most likely to
regress silently.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | `text-base` (16px) / `text-[15px] md:text-lg` variants already in use | 400 | 1.5–1.6 |
| Label / caption | `text-[11px]`–`text-xs` | 500 | normal |
| Heading (H2/H3 card) | `text-xl`/`text-2xl` | 500 | 1.1–1.2 |
| Display (H1/H2) | `clamp()` per-component, see below | 400, `.display` | 1.02–1.1 tuned per instance |

### 🔒 Locked — do not touch to accommodate Spanish

Every `.display` heading in the codebase uses a component-tuned fluid `clamp()`
+ an explicit `leading-[…]` (or the shared `.display` `line-height: 1.02`).
These are Phase 5 deliverables, verified against exact line counts at four
viewports. Examples on file today: `Hero.tsx:114`
(`clamp(1.625rem,3.571vw+0.911rem,2.625rem) md:clamp(42px,4.2vw,58px)`),
`CTASection.tsx:38`, `manifesto/page.tsx:206` (`leading-[1.05]`),
`features/page.tsx:890` (`leading-[1.05]`), `ChangelogItem.tsx:97`
(`leading-[1.1]`), `changelog/page.tsx:906`. **Do not edit any of these values
in this phase, in either locale's render path.** Spanish and English share the
same clamp/line-height per heading — locale-specific type scales are explicitly
out of scope and would themselves be a design regression (two different rhythm
systems for the same layout).

### Text-expansion contract (the acceptable vs. the not-acceptable)

Spanish averages ~15–25% longer than English. The contract:

| Outcome | Status |
|---|---|
| A heading that wraps to **more lines** in Spanish than it did in English | **Acceptable and expected.** `text-balance` + `max-w-*` exist precisely to reflow. |
| A heading or paragraph **wider than its own box** (text overflows horizontally) | **Not acceptable.** This is exactly what `e2e/containment.spec.ts` Sweep A measures (`scrollWidth > clientWidth`). |
| Content **escaping a clipping ancestor** (e.g. a card's `overflow-hidden` wrapper) | **Not acceptable.** Sweep B. |
| Shrinking the `clamp()` min/max to make a long Spanish string fit on one line | **Not acceptable as a fix.** Do not diverge the two locales' type scale. If a Spanish string is disproportionately long, shorten the *copy* (register still applies — infinitive CTAs are naturally compact), not the font size. |

**Acceptance measurement:** `npm run` the containment suite (`e2e/containment.spec.ts`)
against both locale route trees. See "Containment Harness Expectations" below
for exactly what "both locale route trees" means today (it does not happen for
free).

### Glyph & diacritic verification — required, not optional

`.display` is uppercase Special Gothic Expanded One. Spanish needs
`Á É Í Ó Ú Ñ ¿ ¡` (¡ only matters if a copy exception to the no-exclamation
rule is ever granted — assume it is not, see Copywriting Contract).

- The font is loaded with `subsets: ["latin"]` (`layout.tsx:27`). Google Fonts'
  "latin" subset conventionally includes the accented Latin-1 range (á é í ó ú
  ü ñ ¿ ¡), which is distinct from "latin-ext" (Central European diacritics).
  This was **not** verified by rendering in this repo — **the executor must
  render-check it**, not assume it from this note.
- **Required check:** render the string `PORTAL ÁGIL — ¿QUÉ ES EL PORTAL? AÑADIR
  UNA VERSIÓN` inside `.display` at both the mobile-floor and desktop-ceiling
  clamp values (e.g. inside `Hero.tsx`'s H1 slot, or a scratch route). Confirm
  in DevTools: (a) no tofu/`.notdef` boxes, (b) no vertical clipping of the
  accent marks against the tuned `line-height` — an accent sits above cap
  height, and a `line-height: 1.02` box tuned for unaccented English capitals
  has near-zero slack.
- **If glyphs are missing:** add `"latin-ext"` to the font's `subsets` array in
  `layout.tsx` (cheap, no visual change to English).
- **If accents are visually clipped:** the fix is **per-instance**, not global —
  add vertical padding/margin to the specific heading's wrapper element. Do
  **not** raise the shared `.display` `line-height: 1.02` or any of the
  per-component `leading-[1.05]`/`leading-[1.1]` utilities; those are tuned
  values shared with English and changing them changes English's approved
  rendering too.

**Inherited unchanged.** No new colors, no new tokens. The language switcher
reuses existing tokens exactly as Navbar/Footer links already do — it does not
introduce a new accent usage.

| Accent (10%) | `--color-ep-accent` (`#4487D6`) / `--color-ep-accent-light` | CTA buttons, focus states, the *current* nav link — **not** the language switcher's active state (see below) |

## Copywriting Contract

### Register — LOCKED (07-CONTEXT.md, 07-RESEARCH.md §7)

`tú`, subject pronoun always omitted, infinitive for CTAs/buttons, no `usted`
anywhere, `vosotros` fine, locale code `es` (not `es-ES`). Full priority-ordered
rule list lives in `07-RESEARCH.md` §7 — treat it as binding, not advisory.

### Confirmed CTA translations (already locked as examples in `07-RESEARCH.md` §7 / `07-CONTEXT.md`)

| Element | English (current code) | Spanish |
|---------|------------------------|---------|
| Primary CTA (Hero, CTASection) | `Open El Portal` (`Hero.tsx:148`, `CTASection.tsx:58`) | `Abrir El Portal` |
| Secondary CTA (Hero) | `Read the methodology` (`Hero.tsx:159`) | `Leer la metodología` |
| Navbar auth link | `Log in` (`Navbar.tsx:75`) | `Iniciar sesión` |
| Navbar primary CTA | `Sign Up` (`Navbar.tsx:78`) | `Crear cuenta` |

Both `Open El Portal` / `Read the methodology` CTA labels sit inside
`<span className="text-nowrap">` (`Hero.tsx:148,159`; `CTASection.tsx:58`). The
Spanish strings above are comparable length or shorter — low risk — but because
the wrapper is `text-nowrap`, any future re-wording of these specific strings
must be re-measured against button width at 320px before merge (buttons stack
`flex-col` below `md:`, so width pressure is a desktop-only concern here, not
a mobile one).

### Product vocabulary — DERIVED, not authored (D-01/D-02, locked)

Do not invent Spanish product terms. Pull them from the app's own
`es.json`/`en.json` key pairs (`/home/danitrrga/dev/Projects/el-portal/src/messages/`).
Confirmed split already extracted in `07-CONTEXT.md`:

| English | Spanish | |
|---|---|---|

| Cycle | Ciclo | translated |
| Day | Día | translated |
| Habits | Hábitos | translated |
| Goals | Objetivos | translated |
| Score | Puntuación | translated |
| Archives | Archivos | translated |
| Trends | Trends | **kept English** |
| Dashboard | Dashboard | **kept English** |
| Cinema | Cinema | **kept English** |
| Pulse | Pulse | **kept English** |

Any term outside this table must be looked up in the app's `es.json`, not

### Spanish anti-words list (new — extends BRAND.md's English list)

`BRAND.md`'s anti-words list is English-only and the canonical refs flag it as
needing a Spanish equivalent. This phase supplies it — treat as equally binding:

> moderno, elegante, estilizado, desatar, elevar (as a verb of ambition — "elevar
> tu vida"), de última generación, revolucionario, que cambia las reglas del
> juego, potente/poderoso, hermoso, inmersivo, fluido/sin fricciones (as
> marketing filler — "seamless"), vanguardista, potenciar (as hype — "potencia
> tu día"), desbloquear (as hype — "desbloquea tu potencial"), empoderar.

**Copy rules carry over unchanged:** no exclamation marks anywhere (this bans
`¡…!` in Spanish too — there is no locale exception), no em-dashes substituting
commas.

### Punctuation convention

- **Inverted marks (`¿` `¡`):** `¿` is permitted for genuine questions in prose
  (rare on this site — headings here are declarative, not interrogative,
  per `BRAND.md`'s "Disciplined" principle). `¡` is **not permitted** — it is
  inseparable from an exclamation, and exclamations are already banned
  site-wide. If a heading needs `¿…?`, both marks are required — never drop the
  opening `¿` to save width, that is not a stylistic option in Spanish.
- **Quotation marks:** match the existing English convention (straight double
  quotes, used sparingly). Do not introduce Spanish guillemets (`«»`) — that
  would be a second typographic language on the same page next to English
  content (nav, unprefixed routes) and reads inconsistent within one site.
- **Dashes:** en-dash usage in prose (e.g. `CTASection.tsx:51` "tracks,
  analyzes, and surfaces patterns — you focus on the work") should translate to
  the equivalent Spanish em/en-dash construction, not a comma splice — the
  "no em-dash substituting commas" rule bans em-dashes *replacing* commas, not
  em-dashes used correctly as the current English copy already does.

### Legal pages authority notice (D-07, locked)

Both `/privacy` and `/terms` get a visible notice: **English governs in case of
discrepancy.** Placement: directly under the H1, before the first body
paragraph, styled as existing meta text (`text-sm`, `--color-ep-fg-muted`) — not
a banner, not a colored callout box (no new visual chrome for this; it is a
sentence, not an alert).

### Empty / error / destructive states

Not applicable. This is a static marketing site — no forms, no client-side data
fetching, no destructive actions, no `not-found.tsx` exists in the codebase
today (a Spanish 404 page is out of scope for this phase; if one is ever added,
it inherits this same register contract).

## Language Switcher — Component Spec

The one new UI control this phase introduces. Constraints below are additive
specification on top of the LOCKED decisions in `07-CONTEXT.md` D-10/D-11/D-12 —
read those first; this section says *precisely* how to build what they already
decided, it does not reopen them.

### Visual

- **Text toggle, literal `EN / ES`.** No flag icons (D-10). Render as two
  `Link`s with a static `/` separator between them:
  `<Link>EN</Link><span>/</span><Link>ES</Link>`.
- Typography: same as adjacent nav/footer link text — `text-sm font-medium`
  (Navbar context) or `text-sm` (Footer context). Do **not** introduce a new
  type role for this control.
- Active locale: `text-[var(--color-ep-fg-strong)]` + `aria-current="page"`.
  Inactive locale: `text-[var(--color-ep-fg)] hover:text-[var(--color-ep-fg-strong)]
  transition-colors duration-300` (matches `Navbar.tsx:59-64` exactly).
  Separator `/`: `text-[var(--color-ep-fg-subtle)]`, non-interactive.
- No border, no pill background, no badge chrome. This is a link pair, not a
  button group — consistent with "One accent per surface" (`BRAND.md`) and
  with the fact that no other Navbar link gets a background treatment.

### Placement (D-11: nav on desktop, footer on all viewports)

- **Navbar (`Navbar.tsx`):** add to the "Right Actions" cluster
  (`Navbar.tsx:73-100`), positioned **before** the "Log in" button, wrapped in
  `hidden md:flex items-center` (mirrors the existing `hidden md:flex` desktop
  nav-links pattern at line 55). It does **not** appear in the mobile hamburger
  panel (`#mobile-nav`, lines 105-132) — mobile users reach it via the footer
  only. This is the locked tradeoff in D-11, not an omission to fix.
- **Footer (`Footer.tsx`):** add to the bottom bar (`Footer.tsx:104-123`),
  between the copyright paragraph and the decorative wordmark, so the row reads
  `© year El Portal… | EN / ES | [wordmark]` on `sm:` and up, and stacks in
  that same order on mobile (the bottom bar is already
  `flex-col gap-10 sm:flex-row sm:items-center sm:justify-between sm:gap-6` —
  add the switcher as a third flex child using the same gap rhythm, do not
  invent a new gap value). This is the one place this phase is authorized to
  add a new element to an existing flex row — it is new scope (I18N-03), not a
  "fix," so it is exempt from the Phase 5 "additive-only, never touch existing
  desktop layout" rule, but must still use only tokens/spacing already in the
  file.

### Touch target (D-11: 44px minimum, inherits the RESP-03 pattern)

Reuse the exact pattern already used for the Footer's own links
(`Footer.tsx:92`: `flex min-h-11 items-center … md:min-h-0`) and the Navbar
logo link (`Navbar.tsx:50`): `min-h-11` by default, `md:min-h-0` to not force
row height at desktop where the surrounding row is already taller than 44px.
Apply this to **each** of the `EN`/`ES` links individually (not to the wrapping
group), so the tap target for each locale choice is independently ≥44×44 CSS px
on coarse-pointer viewports — this is what `touch-targets.spec.ts` measures per
element, not per group.

⚠️ **Tablet/coarse-pointer edge case to verify, not assume:** `RESPONSIVE.md`
flags that `pointer-coarse` is not synonymous with "narrow viewport" — a
touchscreen laptop can report `hover:none, pointer:coarse` at desktop widths,
which is exactly where the Navbar instance (visible from `md:` up) lives. Run
`touch-targets.spec.ts` against the `touch-iphone` project and any
coarse-pointer desktop-width project already in `playwright.config.ts` before
calling this control done — do not assume the `md:min-h-0` collapse is safe
without that check.

### Behavior (D-12: preserves current route)

`/es/pricing` ↔ `/pricing`, never a bounce to `/` or `/es`. Use next-intl's
locale-aware `Link`/`usePathname` (per `07-RESEARCH.md` §4) rather than a raw
`next/link` href swap — with `localePrefix: "as-needed"`, the English path has
no prefix to strip/add, which is exactly the case next-intl's routing helpers
exist to handle correctly. This is implementation, not visual design, but it is
recorded here because getting it wrong (e.g. a naive string-prepend that leaves
a stale `/es` on the English side) is a visible interaction bug, not just a
routing bug.

## Containment Harness Expectations

`e2e/containment.spec.ts` is the harness most likely to fire on Spanish copy —
say so explicitly rather than leaving it implicit.

- **`ROUTES` (`e2e/support/pages.ts:5-13`) is currently 8 flat English paths.**
  It does not know about `/es/*` yet. Extending it to cover both locales is a
  planning/implementation task, not a design decision — but the **design
  contract's acceptance bar is:** the Sweep A / Sweep B checks in
  `containment.spec.ts` must be run and pass (or have a new, individually
  justified `KNOWN_UNFIXED` entry — see below) against **every one of the 8
  routes in both `en` and `es`**, not just `en`.
- **`KNOWN_UNFIXED` entries are keyed by exact route string** (`route: "/pricing"`,
  etc. — `containment.spec.ts:44-84`). They do **not** automatically cover a
  locale-prefixed route like `/es/pricing`. Do not assume KU-1…KU-4 "carry over"
  silently:
  - If the underlying English defect (e.g. KU-4, the 77px pricing comparison
    table escape) is still present verbatim on the Spanish route because it is
    layout-caused, not copy-caused, it needs its **own** `KNOWN_UNFIXED` entry
    for the `/es/pricing` route path (same `ref` id is fine, reuse it — it is
    the same underlying defect, just now also visible on a second route
    string).
  - If Spanish copy makes an existing English defect **worse** (bigger overflow
    number) or Spanish copy **creates a new** offender that does not exist in
    English, that is a **new** finding this phase owns and must fix at source —
    it does not inherit KU status by association.
- **New offenders this phase introduces must be fixed, not suppressed**, with
  one narrow exception mirroring the existing KU pattern: if a fix would
  require touching the frozen desktop clamp/line-height values (see Typography
  above), stop and flag it for a design decision rather than silently editing a
  Phase 5 tuned value.

## Layout-Sensitive Components Checklist

Enumerated, file-anchored, in priority order by risk. "Truncate" (ellipsis) is
lower risk than bare "nowrap" (no ellipsis, grows instead) — the table below
says which pattern each offender uses.

| Component | File:line | Pattern | Risk | Contract |
|---|---|---|---|---|
| Navbar desktop links | `Navbar.tsx:55-70` | normal wrap, `space-x-8` | Low | Links are single short words (`Manifesto`, `Changelog`, `Features`, `Pricing`); Spanish equivalents (`Manifiesto`, `Registro de cambios`, `Funciones`, `Precios`) are comparable or shorter. No fixed width — safe by construction. |
| Navbar auth CTAs | `Navbar.tsx:74-79` | `whitespace-nowrap` (Button primitive) | Low-Med | `Iniciar sesión` (14 ch) vs `Log in` (6 ch) — button grows, does not wrap. | Hero/CTASection primary CTA | `Hero.tsx:148,159`; `CTASection.tsx:58` | `text-nowrap` span inside Button | Low | See Copywriting Contract — translations already measured comparable length. |
| Pricing plan badge ("Most Popular" style) | `pricing/page.tsx:424-434` | `whitespace-nowrap`, absolutely centered, **no `max-width`** | **High** | Badge is `left-1/2 -translate-x-1/2` with no width constraint — grows symmetrically from center with no ellipsis fallback. Before shipping the Spanish badge string, measure its rendered width against the narrowest pricing card at 320px. | Pricing comparison table | `pricing/page.tsx:243-300` | `overflow-hidden` wrapper, no `data-reflow-exempt` | **High (pre-existing, KU-4)** | Already escapes its wrapper by 77px at 320px in English (logged, unfixed, `deferred-items.md`). This table is also a reasonable `data-reflow-exempt` candidate per `RESPONSIVE.md`'s 2-D-layout exception — that reclassification is a design decision for the planner to weigh, not something this UI-SPEC resolves unilaterally, since it would suppress the containment check rather than fix the layout. |
| Legal-copy paragraphs (`/privacy`) | flagged in `containment.spec.ts` as KU-3 | normal wrap | Low-Med | Already known-overflowing in English at 320-390px. Spanish legal prose (D-07/D-08, human-reviewed) will very likely be longer — re-measure KU-3's overflow numbers against the Spanish route once translated; if they grow materially, that is signal the underlying paragraph width/line-height (not the KU suppression) needs the fix Phase 5 deferred. |
| `/mcp` prose paragraphs | KU-2 | normal wrap | Low-Med | Same pattern as KU-3 — pre-existing English overflow at narrow widths, watch for growth under Spanish, do not let it silently inherit KU status without re-measuring. |
