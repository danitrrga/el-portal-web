<objective>
Translate every changelog entry — roughly 170 strings, the largest single
translation job in the phase — into `src/messages/es/changelog.json`.

Purpose: plan 07-12 moved the entries into the catalogue, converted dates to
shared ISO values and tags to shared keys, precisely so this plan is a
one-file prose write. That structural work removed one date string and one tag
string per entry from the surface before translation started.

Entry parity is the requirement that matters here. A Spanish changelog missing
three entries still looks complete to a reader, which is the exact failure mode
research §6 flagged as worse than not translating at all. The parity gate
enforces equal array length, so a dropped entry fails the build rather than
shipping quietly.

COUNT DISCIPLINE. Do not translate "35 entries" or "33 entries" — translate the
entries that exist. An earlier draft of this plan and of 07-12 asserted 35; the
tree holds 33. Plan 07-12 now measures the count into
`.planning/phases/07-spanish-localization/07-12-ENTRY-COUNT.txt` and this plan's
gates compare against `en.entries.length` and that file, so the number cannot rot
again in either direction.

There is one blind spot this plan has to close itself. The phase-wide gates check
KEY and PLACEHOLDER parity, not whether the two locales say different things — so
an English string copied byte-for-byte into `es` passes every gate clean. Nested
prose is where that actually happens, which is why this plan carries its own
narrow identical-value check for the `changelog` namespace only.

Output: `src/messages/es/changelog.json`, complete and passing the gates.
</objective>

This task exists because I18N-07 requires it and because the loss it catches is
invisible by construction: a line carried by a pun, a rhythm, a double meaning or

that. Only this pass can.

Go back over every changelog entry title, bullet and note this plan translated — the Spanish you just wrote, not the English you started
from — and check each string against SPANISH-VOICE.md's four wordplay triggers:

  1. the English turns on a pun, an idiom or a double meaning;
  2. the effect is carried by rhythm or sound that the Spanish loses;
  3. the term has no Spanish equivalent GLOSSARY.md resolves and no
     marketing-only coinage feels right;
  4. the Spanish that preserves the meaning breaks the length budget the
     display clamp allows, so a weaker phrasing shipped instead.

For every string where one fires, append a row to
`.planning/phases/07-spanish-localization/TRANSLATION-FLAGS.md`: key, English
verbatim, the Spanish actually shipped, one concrete sentence on what was lost,
and which trigger fired. The file is APPEND-ONLY — never edit or delete another
plan's rows, and never reorder the table.

Two rules that decide what a row means:

  - The Spanish shipped stays real copy. A row is a request for the design owner
    to re-write a line by hand, NOT a licence to leave the key empty, a
    placeholder, or the English string. The site has to read correctly whether or
    not that rewrite ever happens, and the parity gates fail on a blank anyway.
  - "Sounds worse" is not a row. Spanish here is a re-write in the brand voice,
    so departing from the English is expected and good. A row records a specific
    effect that died, named concretely enough that someone can decide whether to
    fix it.

Zero rows is a legitimate outcome and is a claim you are making. Do not
manufacture rows to look thorough — a padded register is worse than an empty one,
because it buries the lines that actually need attention.
