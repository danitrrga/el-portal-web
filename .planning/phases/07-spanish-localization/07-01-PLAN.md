<objective>
Stand up next-intl on Next 16 and move all 8 routes under a `[locale]` segment
**without moving a single English URL and without any route losing static
prerendering.** No copy is translated in this plan — this is the routing and
contract layer every other Phase 7 plan builds on.

error** — pages simply stop being static. I18N-06 exists to catch exactly that,
so this plan proves staticness mechanically rather than assuming it.

It also declares the contracts later plans consume in parallel: the ten message
namespaces, the `buildPageMetadata` signature, and the locale-aware navigation
exports. Declaring them here is what lets Waves 2-4 run without touching shared
files.

English URLs, plus a machine-checkable proof of the routing contract.

ROUTING CONFIG (src/i18n/routing.ts). Call `defineRouting` from
`next-intl/routing` with locales `['en','es']`, defaultLocale `'en'`,
`localePrefix: 'as-needed'` (locked — English URLs must not move), and
critically `localeDetection: false`. Export the `routing` object and a `Locale`
type derived from `routing.locales`.

`localeDetection: false` is load-bearing and is the single most likely thing to
get wrong. next-intl's default middleware negotiates on EVERY unprefixed
pathname, so with detection left on, a Spanish-preferring browser requesting
`/pricing` is redirected to `/es/pricing`. That directly violates I18N-02 ("no
other URL auto-redirects by language") and is the SEO defect 07-RESEARCH.md
section 1 was written about. Detection is disabled in the library and
re-implemented by hand for the single `/` pathname in the proxy.

NAVIGATION (src/i18n/navigation.ts). Export `Link`, `redirect`, `usePathname`,
`useRouter`, `getPathname` from `createNavigation(routing)`. These are what make
D-12 (locale switch preserves the current route) correct under `as-needed`,
where the English path has no prefix to strip.

REQUEST CONFIG (src/i18n/request.ts). Use `getRequestConfig` from
`next-intl/server`. Resolve the locale with `hasLocale(routing.locales, await requestLocale)`
falling back to `routing.defaultLocale`. Load and merge all ten namespaces from
the `<interfaces>` block by dynamic-importing
`../messages/${locale}/${namespace}.json` for each, and return `{ locale, messages }`
with `messages` keyed by namespace name. Keep the namespace list as a single
exported const array so adding a locale or namespace is a data change, not a
refactor (the deferred-idea requirement in 07-CONTEXT.md).

PROXY (src/proxy.ts). Next 16 renamed `middleware.ts` to `proxy.ts`; for a
`src/`-based project it lives at `src/proxy.ts`, a sibling of `src/app/`, and
exports a default function plus a `config.matcher`. Create
`handleI18nRouting = createMiddleware(routing)` once at module scope. In the
default export, negotiate ONLY when `request.nextUrl.pathname === '/'` —
every other pathname is delegated straight to `handleI18nRouting` untouched.

Negotiation precedence at `/`, exactly as locked in ROADMAP.md: first the
`NEXT_LOCALE` cookie if it holds a value in `routing.locales`; otherwise the
`Accept-Language` header, ordered by negotiator's `languages()` and resolved
with `@formatjs/intl-localematcher`'s `match()` against `routing.locales` with
`'en'` as fallback — this is what makes `es-AR` and `es-419` resolve to `es`
instead of falling through to English (research section 4); otherwise `'en'`.
If the result is `'en'`, fall through to `handleI18nRouting` so `/` serves
English with no redirect. If the result is `'es'`, redirect to `/es`.

REDIRECT CONSTRUCTION — closed pathname, preserved query. Clone
`request.nextUrl` (`const url = request.nextUrl.clone()`), assign
`url.pathname = '/es'` as a literal from the closed locale set, leave
`url.search` exactly as it arrived, and redirect to that URL.

The pathname stays closed because a request-controlled pathname is an open
redirect (threat T-07-01-03) — never derive it from a header, query parameter or
cookie, and never touch `url.host`, `url.protocol` or `url.port`. The query
string is different: it is data the destination page receives, not a navigation
target, and dropping it silently destroys campaign attribution. A visitor
arriving at `/?utm_source=newsletter` with a Spanish browser must land on
`/es?utm_source=newsletter`, not on a bare `/es`. Hash fragments never reach the
server, so there is nothing to preserve there.

Assert both halves in `scripts/verify-locale-routing.mjs`: the `location` header
for `/?utm_source=test&x=1` under a Spanish `Accept-Language` must end in
`/es?utm_source=test&x=1`, and the `location` for a request whose query attempts
a path escape (for example `/?next=https://evil.example`) must still have
pathname exactly `/es` with the origin unchanged.

A request with NO `Accept-Language` header and no cookie must resolve to `'en'`.
That is the Googlebot case and the whole reason blanket redirection was
rejected; assert it in the verification script rather than reasoning about it.

Set the matcher to `'/((?!api|trpc|_next|_vercel|.*\\..*).*)'` so static assets,
`/icon.svg` and `/apple-touch-icon.png` never enter the proxy.

WHO OWNS `NEXT_LOCALE` — state this in a comment at the top of `src/proxy.ts`,
because the phase has a real loop bug the moment the two halves disagree.

  The CLIENT owns an EXPLICIT choice. `LanguageSwitcher` (plan 07-04) writes
  `NEXT_LOCALE` to the locale the reader selected BEFORE it navigates, with
  `path=/`, `max-age=31536000`, `SameSite=Lax`. The proxy never overwrites an
  explicit choice.

  The PROXY only READS the cookie, and only at `/`.

That split is not a preference — it is the fix for a loop the proxy cannot
escape on its own. Without a client-side write, this sequence never terminates:
a reader on `/es` clicks EN, `localePrefix: 'as-needed'` sends them to the
unprefixed `/`, the `/` negotiation reads the still-`es` cookie, and sends them
straight back to `/es`. English becomes unreachable through the site's own
control. Plan 07-04 Task 1 implements the write; this plan's job is to make the
proxy compatible with it and to say so where the next reader will look.

Consequently: do NOT have the proxy write `NEXT_LOCALE` on the basis of a
prefixed pathname. Verify empirically whether `createMiddleware` writes the
cookie when `localeDetection` is false. If it does, that is acceptable only
because the switcher's synchronous write happens first and any middleware write
would agree with it; if it writes a value that DISAGREES with the request's own
locale prefix, disable that behaviour. Record what you observed in the summary —
plan 07-04 depends on the answer and must not have to rediscover it.

`httpOnly` stays `false`: the value is a two-letter UI preference the switcher
reads and writes from client script, not a secret.
